# 参考接线解析规则

> 权威依据：[docs/assetCardWorkflowPlan.md](../../../../docs/assetCardWorkflowPlan.md) §1.2、§1.3、§2 K2；[docs/assetCardWorkflowPlanReview.md](../../../../docs/assetCardWorkflowPlanReview.md) A4；[docs/localStoryCanvasStudy.md](../../../../docs/localStoryCanvasStudy.md) §2（LSC 原实现的降级来源）。
> 卡片本身的写法见 [资产卡模板](assetCardTemplate.md)。解析结果写进工作区 `plan/assetIndex.json`：常规路径由画布「导入资产与分镜」节点（`packages/nodes/assetImportNode`）独占写入；`planOperator` 里只有 `build` 会写它（`packages/tools/planOperator/src/index.ts:293`、报告在 `:300`），`resolve` 只把索引结构返回给调用方、**零写入**（`:229-244`）。（P2 之前由 Agent 按本规则手写。）
> 编号在资产卡里可宽口径书写，但**索引里一律规范化**；本节的编号示例均为规范化后的形态。

---

## 一、解析总原则

1. **显式 > 派生 > 兜底**：作者写明的字段永远优先，Agent 不自行猜测；三级都没命中就**不接线**，按原文独立生成。
2. **解析必须可复现**：同一样例在两次不同会话里产出字节级相同的 `refs`（`order`、`nodeId` 之外），否则视为漂移。
3. **守卫优先于结果**：哪怕三级里的某一级给出了候选，只要被任一道守卫拦下，一律记为不接线并写 `warnings`。
4. **接线即顺序**：`refs` 数组顺序 = 画布参考位次 = 生成时参考顺序；作者直接写官方 `<Picture N>` / `<Video N>` / `<Audio N>`，每个类型的 `N` 独立从 1 起，位次取自该类型资产在 `refs` 数组中的先后（同类型去重后按出现顺序，图片/视频/音频之间互不干扰），见 [多轨工程模板](multitrackTemplate.md) §四。引擎下发不再换算，标记原样进入六段文本，最终由 `buildPrompt`（`packages/nodeShared/src/mtrack/mediaDispatch.ts`）拼装、由 `composeClipRequest` 按媒质分组越界检查。

### 1.1 编号规范化（写入索引前统一执行）

| 规则 | 例 |
|---|---|
| 数字补足 2 位，**不截断** | `C1` → `C01`；`C123` → `C123` |
| 状态后缀统一大写 | `c01-b` → `C01-B` |
| `SC` 必须先于 `C` 匹配 | `SC01` 不能被 `C` 前缀吃成 `C01` |
| 分隔符统一为一个空格 + `·` | 仅影响展示，不影响 ID |

规范化后的 ID 正则：`^(?:C|SC|P|KF)\d{2,3}(?:-[A-Z])?$` 或 `^S\d{2,3}(?:-[A-Z])?$`。卡片正文里写 `C1`、`c01-b` 不算错，规范化时按上表处理，且**不与已存在的 `C01` 判重**（审阅 A4）。

## 二、三级优先级

| 级 | 名称 | 输入来源 | 通过条件 |
|---|---|---|---|
| L1 | **显式声明** | 卡片字段 `身份参考`/`结构参考`/`道具参考`（含别名）的值 | 值里取出的编号**前缀与卡类型匹配**、目标卡存在 |
| L2 | **参考派生散文** | 卡片字段 `参考派生`（含别名）的正文 | 命中正向短语表**且不命中**否定词表 |
| L3 | **正则锚点兜底** | 卡片正文字（提示词、说明、备注等整块） | 按类型命中锚点窗口内的候选，且否定词不在同一子句 |

### L1 显式声明

- 值里「注释」随写，只取编号：`身份参考：C01（同一张脸，仅更换服装）` → `C01`。
- 可写多个编号（构图卡常见）：`（引用 C01、SC01、P01）` → `["C01","SC01","P01"]`，按书写顺序。
- **前缀写错视为未声明**，直接落到 L2，不报错也不接线：人物卡写 `身份参考：SC01`、道具卡写 `道具参考：C02` 都属于此类。
- 显式声明**仍然会被 backwards-only 与群像/闪回守卫拦截**（见 §三），被拦时不静默接线，改记 `warnings`。

### L2 参考派生散文

- **正向短语表**（命中任一即算有意图）：`为同一角色`、`同一角色`、`同一空间`、`同一器物`、`同一张脸`、`保持脸部结构`、`绑定为本卡参考图`。
- **否定词表**（命中任一即否决本卡派生）：`两名`、`两人`、`同装同使命`、`区分`、`混同`、`不是`、`并非`、`不与…共用`、`独立设卡`。
- 只取**同前缀、非自身**的第一个编号。派生散文是给「写法松散但意图明确」的作者用的兜底，不是给推理留的口子。

### L3 正则锚点兜底

| 卡类型 | 锚点（命中任一） | 窗口 | 候选取值 |
|---|---|---|---|
| 人物 `C` | `同一张脸`、`同一人脸`、`保持同一身份锚点`、`延续…面部骨相` | ±(16,24) 字 | 靠锚点**左侧最近**的 `C` 编号优先 |
| 场景 `SC` | `同一(棵古槐\|棵树\|空间\|布局…)`、`与 SC16 是同一…`、`须与 SC22 一致` | ±40 字 | 窗口内最近编号 |
| 道具 `P` | 同类「同一器物/同一形制」表述 | ±40 字 | 窗口内最近编号 |

- 否定判定在**同一子句**内进行，子句切分符为 `\n`、`。`、`；`、`;`。
- 三级都没命中 → `refSource: "none"`，`refs: []`，不接线。

`refSource` 只取 `explicit` / `directive` / `fallback` / `none` 四个值，与 `plan/assetIndex.json` 的字段对齐。

## 三、四道守卫（按顺序判定，任一不过即拒绝）

| # | 守卫 | 判定 | 拦截后的动作 |
|---|---|---|---|
| G1 | **存在性与前缀匹配** | 目标卡必须在**同一份** `assets/assetCards.md` 内存在；取出的编号前缀必须与卡类型匹配 | 不接线；L1 前缀不符时落到 L2，L2/L3 命中但前缀仍不符则丢弃该候选 |
| G2 | **否定守卫** | 卡片正文里出现否定词（L2 表 + L3 子句判定） | 不接线，写 `warnings` |
| G3 | **backwards-only** | 目标的 `order` 必须**小于**本卡的 `order` | **一律拒绝，显式声明同样拦截**，写 `warnings` |
| G4 | **群像/闪回排除** | 正文命中 `少年`/`闪回`/`回忆`/`年轻时`/`弱冠`；或基卡名含 `群`/`同式`/`众` | 自动接线（L2/L3）一律拒绝；**显式声明仍接线，但追加 `identityConflict` 警告** |

- **G3 为什么连显式声明都拦**：前向引用会让 `refs` 依赖尚未生成的资产，拓扑排序时直接死锁（LSC §3.2 的「避免死锁」）。发现前向引用时正确的修法是**调整卡片在源文件中的顺序**，或在正文里补一句合法声明，不是强行接线。
- **G2 为什么人物侧必须补**：LSC 原实现只在道具/场景侧挂了否定守卫，人物侧是自认缺失的缺陷（[LSC 报告 §2.2](../../../../docs/localStoryCanvasStudy.md)）；`与 C01 以服装区分` 这类文字会被人物锚点误接。本方案在**全部三类**上统一挂否定守卫。
- 候选中若显式写了多个编号，逐枚应用 G1–G4；通过的编号按原书写顺序进入 `refs`，被拦的编号逐个记 `warnings`（不是整卡作废）。

## 四、状态后缀回落规则

- **未声明的后缀卡继承基卡**：`C03-B` 没有 `身份参考` 字段时，回落到 `C03`，`refSource: "fallback"`。
- **两兄弟都有后缀时**（如 `C05-A 完整` 与 `C05-B 拆开`，均无声明）：取**源文件中出现次序第一张**的后缀卡。这是对 LSC 实现的修正——LSC 用 `siblings[0]` 取字典插入序，移植时改为按 `order` 升序取第一张，保证可复现。
- 基卡本身存在且在后（`order` 更小）时才允许继承；否则触发 G3。
- `P01-A`/`P01-B`、`SC01-A` 等同理，规则只按「同前缀 + 同数字」判兄弟。

## 五、样例

### 正例 1（L1 显式声明）

```markdown
### C02 · 淳于棼（重伤）
- 身份参考：C01（同一张脸，带伤）
- 提示词：同一张脸的青年沈砚，面色苍白，左颊一道血痕，衣袍破损
```

`C02` 的 `order` 大于 `C01` → G3 通过；无否定词 → G2 通过。

```jsonc
{ "id": "C02", "refs": ["C01"], "refSource": "explicit" }
```

### 正例 2（L2 参考派生散文）

```markdown
### P02 · 八仙桌（旧）
- 参考派生：与 P01 为同一器物，用久成旧
- 提示词：同一张八仙桌，桌面磨损发亮，边角磨圆
```

命中正向短语「为同一器物」，未命中否定词，`P01` 与 `P02` 同前缀且更早出现：

```jsonc
{ "id": "P02", "refs": ["P01"], "refSource": "directive" }
```

### 正例 3（L3 正则锚点兜底）

```markdown
### SC02 · 古槐树下（雨夜）
- 提示词：与 SC01 是同一棵古槐，暴雨初歇，地面水洼反光，空镜无人
```

无参考字段、无 `参考派生`；L3 场景锚点「是同一棵古槐」在窗内命中，取左侧最近的 `SC01`，同一子句无否定词：

```jsonc
{ "id": "SC02", "refs": ["SC01"], "refSource": "fallback" }
```

### 反例（误接负例：与 C01 以服装区分）

```markdown
### C04 · 淳于棟（孪生兄弟）
- 提示词：与 C01 以服装区分，容貌相同但气质阴郁，深色劲装
```

- L1：无参考字段。
- L2：无 `参考派生` 字段。
- L3：人物锚点表可能命中「同一张脸」类表述，或靠锚点左侧最近的 `C01` 取到候选；但同一子句含否定词「区分」→ **G2 拦截**。

结论：`refs: []`、`refSource: "none"`，并写一条 `warnings`：

```jsonc
{ "card": "C04", "code": "identityConflict",
  "message": "命中否定词「区分」，不自动接线；若确需同一张脸，请改为显式声明：身份参考：C01" }
```

> 该负例即 LSC 的人物侧缺陷在本方案下的正确行为：**宁可漏接、不可误接**。误接会让两个角色共享脸部锚点，后续每段视频都带着错脸。

## 六、与校验器的对应关系

| 本规则 | `planOperator` 校验 |
|---|---|
| G1 存在性与前缀 | V2 |
| G3 backwards-only | V3（显式声明同样拦） |
| 构图卡必须有母版参考、不参与派生 | V4 |
| 群像/闪回、否定命中 | 记入 `warnings`（`identityConflict` 等） |
| 索引规范化（补零/大写/`SC` 优先） | V1（编号唯一与合法性） |

解析结果与画布入边、参考顺序（`data.referenceOrder`）的逐位对账见 [多轨工程模板](multitrackTemplate.md) §四，对应 V6/V7/V15。

对账口径是官方 `<Picture N>` / `<Video N>` / `<Audio N>`：参考顺序决定每种类型的位次，第 1 张图片写 `<Picture 1>`、第 2 张写 `<Picture 2>`；视频、音频各自独立编号。注意 `referenceIds` 可能混入 `kind: "sound"` 的音频卡（V8 图片 ≤9、音频 ≤1，分开计），同类型内部按出现顺序连续编号、不跳号，类型之间互不干扰。引擎下发不再换算，标记原样进入六段文本，最终由 `buildPrompt` 拼装、由 `composeClipRequest` 按媒质分组越界检查；正文出现旧「双花括号 ref 占位符」一律报错。
