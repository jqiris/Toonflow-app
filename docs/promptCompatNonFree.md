# 非 freevideo 供应商提示词格式保留方案

> **状态：过程稿，方案未采纳（2026-10-23）。** 本轮最终落地的是「保留三字段存储 + 参考标记统一 `{{ref N}}`」，未做单串改造。本文档保留作为 master 基线与风险评估记录，文中的「单串」实现清单不作为执行依据；现行口径见 `packages/skills/assetCard/references/multitrackTemplate.md` §四 与 `generationRunbook.md` §四。


> 范围：Seedance 2.0 / 2.5、Seedream、Nanobanana（Gemini）、Wan 2.6 的提示词结构、参考标记写法、编号规则与默认值。
> 目的：把默认改成 freevideo / MiniMax-H3 之后，master 时代这些供应商仍能被正确书写、且不因默认切换而受损。
> 性质：**只设计与讨论，不实施**。本文不改 `packages/skills`、不改业务代码、不改 DSH 技能包。
> 基线：`docs/promptCompatBaseline.md`（master 基线盘点）。差异：`docs/promptCompatDelta.md`（相对 master 的 58 处改动）。

**写作约定（全队遵守）**：本文不出现双花括号模板字面量。凡原文档里以双花括号包裹的参考占位，本文一律代写为全角形式 `｛｛ref N｝｝`，含义不变。官方标记 `<Picture N>`、`<Video N>`、`<Audio N>` 属运行期语法，可直接书写。

## 一、结论先行

1. master 的兼容性不是「一套三段式」，而是**「模型 = 唯一路由键 → 每条路由一个可判定外壳 → 模板内容与传输标记分离 → 执行层只搬运 → 单向校验不回流」**。我们改默认模型本身没有破坏这套结构；破坏来自五处**把供应商这一维抹掉、或把某供应商的执行行为写成通则**的表述（§四 NF-1 ～ NF-5）。
2. 五张格式卡里，只有 Seedance 2.0 在三条链路各有不同外壳（A9.1 / 画布三段式 / v118 中文三段式）；2.5 只有 A9.2 一种；Seedream、Nanobanana、Wan 全部只存在于 `v118workflow` 的知识文件里。**默认一旦改成 freevideo，这三条路径的可达性就完全依赖 v118 的入口是否还开放**——这是当前最大的单点风险。
3. 参考标记分三套体系，任何方案都必须保留这个三分法：**供应商私有标记（`<Picture N>`）**、**画布传输编号（旧REF占位标记，全局序号）**、**用户身份句柄（`@角色名_v2`、`#场景名`、`node/image-xxxx`，原样引用）**。三者基数不同，不能互相换算（`canvas/SKILL.md:107` 已把这条写清，应升格为全局规则）。
4. 唯一确定的事实边界：wire 层只对 freevideo 做标记换算（`packages/nodes/videoGenerationNode/src/index.vue:228`）。引导层若对非 freevideo 承诺「生成时会自动换算」，就是假承诺（见 NF-3）。
5. 一句话共存原则见 §六；形态 × 供应商的交叉矩阵见 §七，其中三格是硬冲突（多轨 × 非 freevideo），必须由用户拍板（§九）。

## 五、三类标记的交接契约（实现无关的一段话）

写作者只负责两件事：**用哪套标记**、**编号从哪来**。执行层只负责一件事：**按选定供应商把标记换成它认识的语法**。当前只有 freevideo 这一条换算实现存在（`index.vue:228`），所以：

1. freevideo：写旧标记 → 引擎换算成 `<Picture N>` / `<Video N>` / `<Audio N>` / 「参考 N」文本。
2. Seedance 2.0：写真实句柄或旧标记 + 中文用途声明 → 引擎不换算，**原样进入提示词**。
3. Seedance 2.5：写真实节点 / 句柄 → 引擎不换算，原样进入 `Reference binding`。
4. Seedream / Nanobanana：写旧标记（全局序号）→ 引擎不换算，原样进入图片提示词。
5. Wan：不写标记，首帧由真实图像输入承担。

一句话：**「换算只发生在 freevideo；其他供应商的标记是内容，不是传输编码。」**

## 六、共存原则（一句话 + 展开）

> **默认只回答「没人点名时用谁」，从不回答「怎么写」；一旦用户点名供应商，外壳、标记、编号、语言全部切到该供应商的格式卡，而形态（多轨 / 直连）只决定写进哪个字段。**

展开三条：

1. **路由键唯一**：模型名是唯一路由键，且只在 A0（workflow）/ 模型选择（canvas）一处判定。`workflow/SKILL.md:1009` 原文「每个生成段的正文则按目标模型路由到 A9.1 或 A9.2」已是这个意思，可直接引用。
2. **条件句而非时间句**：所有默认值都写成「用户未点名时…；用户点名 X 时…」。不用「旧版 / 历史 / 作废 / 已迁移 / 兼容层」——默认值会变，能力域不会。
3. **单点定义、单向引用**：每个供应商的外壳只在格式卡里定义一次；其他文件只写「见…」，不复制正文。这正是 `workflow/SKILL.md:43` 已经写明的手法（「本文件不复写 runbook 内容，防止两处漂移」），只是范围应从 runbook 扩到全部格式卡。

- A1 锁能力：多轨只允许 freevideo，UI 下拉收敛，用户要其他供应商就先退出多轨。改动小、不会产出错格式；代价是砍掉一个 UI 已开放的能力。
- A2 保留切换：`clips[].prompt` 的字段结构随供应商切换，runbook §四 的三字段硬门限定为 freevideo 专用。保住能力；代价是要同时维护两套多轨产物格式，且与「多轨产物格式硬隔离」的现有措辞冲突，必须重写那一段。

**岔路 B · v118 的定位怎么写？**
- B1 定位为「模型模板库」：按能力域描述，Seedream / Nanobanana / Wan 模板成为新项目可用入口。
- B2 保留流程复现定位但补入口：承认 v118 流程只服务既有工程，同时把三个模型模板显式登记为可用知识（需在 workflow / assetCard 各加一处「模型 → 模板」索引）。

**岔路 C · 图片默认给谁？**
- C1 维持 freevideo-image 为唯一默认（现状）：成本最低，但点名用户的兜底「按实际可用能力选择」必须补回。

- C3 恢复「按可用能力优先」而不指定具体模型：最接近 master 语义，但把选择权交回模型，可预期性下降。

**岔路 D（低优先）· 标记换算要不要扩到全供应商？**
- 现状只有 freevideo 一条实现（`index.vue:228`）。引导层现在只能选「按现状写清条件」，扩能力属于代码改动，超出本轮「只设计不实施」的范围。建议：引导层按现状写，把「扩换算」列为后续独立需求。
